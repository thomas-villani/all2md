# benchmarks/docx/generate — the generation side

**Windows + a Microsoft Word install only. Hand-run. Never imported by anything CI
executes.** Nothing under `benchmarks/docx/` outside this directory imports
`win32com`, so the scoring side runs on the Linux runner like every other lane.

That split is the same one `benchmarks/pmc` makes between fetching a corpus and
scoring it, taken one step further: PMC commits a manifest and materializes bytes
on demand, but there is no bucket to fetch a scripted DOCX corpus from, so **the
corpus bytes are committed** (the `benchmarks/roundtrip/corpus/synthetic/`
precedent) and CI only ever replays them.

## Why drive Word at all

The documents are generated by scripting a live Word over COM through
[`wordlive`](https://pypi.org/project/wordlive/). The generation script knows
exactly what it put in the document, so it writes an expected-facts record beside
each `.docx` — and Word's own serializer produces the file, so the markup is what
Word really writes rather than what a Python writer thinks Word writes. That is the
PMC lane's "publisher-produced ground truth" principle applied to Office: we do not
author the truth and the artifact with the same tool.

The cost is that generation cannot run in CI, which is why it is quarantined here.

## Running it

```
uv run --with pywin32 python worddoc.py alerts off      # do this first, always
uv run --with pywin32 python numfmt_map.py out.docx     # regenerate numfmt-map.json
```

Word must already be running and visible; `GetActiveObject` attaches to it rather
than starting one, so a generation run happens in front of you and you can watch it.

## The scars

Every item here was learned by hitting it during the 2026-08-23 capability probe
(wordlive 0.19.0, Word build 16.0.20326). `session.py` enforces the ones it can.

- **`Application.DisplayAlerts = 0` before anything else.** One modal — a plain-text
  content control applied to an illegal range will do it — hangs *every* subsequent
  `wordlive` call indefinitely. There is no exit code and nothing to time out
  against; the run just stops. `dismiss-dialogs.ps1` clicks the dialog away over UI
  Automation when it happens anyway.
- **Never hard-code `DocumentN`.** Word's counter is global and advances for
  documents other programs create.
- **`save-as` renames the open document** to the file name. Every later `--doc` must
  use the new name.
- **`WORDLIVE_SAVE_DIRS` must contain the output directory** or `save-as` exits 1.
- **Keep one document open** or Word quits out from under the session.
- **Pin the author** via COM `Application.UserName` before generating tracked
  changes, or `w:ins`/`w:del` carry whoever ran the script and the truth records stop
  being reproducible.
- **`style add --type paragraph` seeds the new style's `rPr` from the cursor's
  paragraph.** Create a style while sitting in a bold heading and you silently get a
  bold style. It also auto-creates a linked character style, which the formatting
  family's truth records have to expect.
- **Two incompatible offset spaces.** `find` offsets count visible text; `range:` and
  `paragraphs` offsets are Word Range offsets, which also count hidden field codes,
  note marks and content-control boundaries. One hyperlink field measured 39
  characters of drift. So: do find-based styling *before* inserting fields, notes,
  content controls or links, or derive from `paragraphs` and confirm with `read text`
  before anything destructive.

## Verified recipes

All confirmed in the saved file's XML, not in the COM object model — the file is
what the parser will see.

| Family | Verdict |
|---|---|
| Raw fields | `fldChar`/`instrText` for `HYPERLINK` and `REF`, `fldSimple` for `SEQ` via `caption`. Word appends `\* MERGEFORMAT`. Insert lands at the *next* paragraph start, and a field at the end of the document splits across `w:p` — keep a spare trailing paragraph. `caption` needs an explicit `": "` separator. |
| Tracked changes | `w:ins`/`w:del` with author and date; a batch's `"tracked": true` restores the prior state afterwards. |
| Style-inherited numbering | Needs the COM `LinkToListTemplate` hatch (`session.link_list_style`) — no `wordlive` verb exists. Produces the exact corporate shape: `numPr` in `styles.xml` only, `w:pStyle` in `numbering.xml`, paragraphs carrying nothing but `pStyle`. Rendered `03) 04) 05)` confirms `decimalZero` + `StartAt`. Leaves an orphan `abstractNum`, which real templates are full of anyway. |
| Content controls | Block SDT when anchored `para:N`, inline when `range:`. `--where after` on an empty control gives a genuine `w:showingPlcHdr` with the PlaceholderText style. Locks work. A plain-text control over a whole paragraph range is one of the hang-modals. |
| Effective formatting | Run carries only `rStyle` while the style carries `w:b`/`w:color` — the case the parser cannot see today. |
| Confirmed present | footnote and endnote references, `gridSpan` merges, `tblHeader` + `cantSplit` repeating headers, OMML, `w:hyperlink` both internal (`anchor=`) and external (`r:id`), continuous two-column sections. |

**One measured limitation.** `insert-equation --display` writes `m:oMath` in its own
paragraph with the Equation style — **not** `m:oMathPara` — so the parser classifies
it `MathInline`. Truth records for wordlive-generated display equations must expect
`MathInline`. Producing a real `m:oMathPara` needs an XML-insertion hatch; until one
exists, the corpus does not get to assert a `MathBlock` it cannot produce.

## `numfmt-map.json`

`WdListNumberStyle` constant → the `w:numFmt` Word actually writes, measured across
constants 0–47. **The COM constant names mislead**: `wdListNumberStyleGBNum1` (26)
writes `decimalEnclosedFullstop`, and `chineseCounting` comes from 37. Choosing a
constant by its name and asserting the `w:numFmt` you expected produces a truth
record that quietly lies, which is why this was measured rather than read off the
documentation.

It is also a sizing for a defect the batch already names. Word writes **46 distinct
`w:numFmt` values**; `_map_numbering_format` in `src/all2md/parsers/docx.py`
recognises **five** of them (`decimal`, `lowerLetter`, `upperLetter`, `lowerRoman`,
`upperRoman`, as of 2026-08-31). The other 41 map to `None`, so the list is not
detected as ordered at all. The unrecognised set is almost entirely CJK, Hebrew and
Arabic numbering — the same blind spot ROADMAP item 18 names for the scoring
corpora, showing up here in the parser itself.
